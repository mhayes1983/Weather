# Weather

The home page (`/`) shows live readings and 24-hour charts from an Ambient Weather station. `/daily` shows the selected station's 16-day forecast and the NWS forecasters' discussion, and both it and the home page switch station through `StationHeader`. `/daily/YYYY-MM-DD` shows one day's hourly detail. `/radar` (labelled Maps) shows a zoomable US map that switches between radar, precipitation type, temperature, clouds, and lightning with warnings, one at a time. `/forecast` (Temperature Forecast) compares daily forecast lows and highs from several sources in one 16-day table, highlighting values well above or below the normal low or high. It loads only when Go is pressed, to save API quota, and its ZIP box starts on the current station's ZIP. `/snow` (Snow Forecast) compares each source's snow total for one storm's dates across several towns, with averages, manual rows for TV outlets and the towns' winter alerts. It also loads only on Go. `/help`, `/terms` and `/privacy` are static pages. Settings (theme and °F/°C) opens from the gear in the top bar, or from the side menu at 720px and below. Default location is Topsham, ME (04086); any US ZIP works. The home page can also show other Weather Underground stations from a configured list. There is no database: station history comes from each station's source on each fetch.

## Layout

- `Weather.Core`: all logic. Must stay free of ASP.NET because the Android app runs it on the phone.
- `Weather.Core.Tests`: xUnit tests. HTTP is stubbed through `TestSupport.cs`; tests never call real services.
- `Weather.Server`: thin API (`GET /api/forecast?zip=`, `GET /api/alerts?station=`, `GET /api/stations`, `GET /api/stations/lookup?q=&source=`, `GET /api/station?id=`, `GET /api/daily-forecast?station=`, `GET /api/daily-forecast/{date}?station=`, `GET /api/discussion?station=`, `GET /api/almanac?station=`, `GET /api/snow/towns`, `GET /api/snow?zips=&start=&end=`, `GET /api/snow/alerts?zips=`). Also serves the built client.
- `weather.client`: React + TypeScript + Vite. No UI or state libraries, apart from Leaflet for the radar map, which loads only on that page.
- `Weather.Android`: .NET MAUI app with no server. It hosts `weather.client`, built with `--mode app`, in a `HybridWebView`. `appBridge.ts` sends `/api` calls through `InvokeDotNet` to `LocalApi` in Core. It has its own `Weather.Android.slnx`, so normal builds don't need the Android tools.

## Commands

```bash
dotnet build Weather.slnx
dotnet test Weather.Core.Tests/Weather.Core.Tests.csproj
dotnet run --project Weather.Server --launch-profile https
```

From `weather.client`:

```bash
npm run build
npm run lint
npm test
```

For the Android app, with the Pixel attached by USB:

```bash
dotnet build Weather.Android/Weather.Android.csproj -t:Run -f net10.0-android
```

The command has no paths because the SDK and JDK are in different places on each machine. The build finds them through `ANDROID_HOME` and `JAVA_HOME`, or in Visual Studio's default folders when those aren't set. Never put one machine's paths in the repo. On a machine without them, install the `maui-android` workload, then run `-t:InstallAndroidDependencies -p:AcceptAndroidSDKLicenses=True` with `AndroidSdkDirectory` and `JavaSdkDirectory` pointing at folders that don't need admin rights, such as under `%LOCALAPPDATA%\Android`. Then set `ANDROID_HOME` and `JAVA_HOME` to them.

This build is debug-signed with each machine's own key, so it can't update an APK built on another machine or released from GitHub, or the other way round. Android uninstalls the old copy, and the app's setup and keys go with it.

The site runs at https://localhost:54777. If the build reports locked files, Visual Studio or another `Weather.Server` process is still running; that isn't a code error.

## Hosting

Runs on TrueNAS as a Docker custom app (`deploy/truenas-compose.yaml`). `.github/workflows/publish-image.yml` publishes the image from `master`. The container serves plain HTTP on 8080, so HTTPS redirection is Development only. User-secrets don't load there, so keys come from environment variables such as `Weather__WeatherUnderground__ApiKey`.

Android releases come from `.github/workflows/android-release.yml`. To release a version, raise `ApplicationDisplayVersion` and `ApplicationVersion` (which must always go up) in `Weather.Android.csproj`. When that reaches `master`, the workflow builds the signed APK and creates the `android-v{version}` tag and GitHub release. A version that's already released is skipped, and pushing an `android-v*` tag still works.

## Rules

- **Temperatures are °F everywhere in Core and the API.** Celsius is display-only, in `weather.client/src/temperature.ts`.
- **Highlighting is decided in Core** (`AnomalyClassifier`), always in °F, so changing units never changes colours. Thresholds are settings, currently 6° either way.
- **One bad source must never break the table.** Sources throw on failure; `ForecastTableService` turns that into a column error, or last good data if it has any.
- **Sources don't take the request's cancellation token.** Results are shared through `WeatherCache`, so each source gets its own timeout.
- **Default column order is most days of data first.** `ForecastTableService` sorts columns by how many dates have a low or high, with ties in registration order (`ServiceCollectionExtensions.cs`) and failed or keyless sources last. Users can hide and drag columns; that's client state and resets on reload.
- **Don't log URLs from the `weather` HTTP client.** Weather Underground's and Ambient Weather's keys travel in the query string, which is why that client's logging is off.
- **Station data stays separate from forecasts.** It's observed, so it uses `IWeatherStation` and `StationService` in `Weather.Core/Station`, not `IForecastSource`. The one exception is `OpenMeteoStation`, which gives model values for a ZIP. It sets `Modelled`, and the Station page must always say it's a modelled estimate. `/api/station` must never expose keys, the MAC address, the street address or coordinates. Configured stations use their configured name, and only a looked-up station shows WU's public neighbourhood.
- **Any well-formed station ID is accepted.** `StationDirectory` returns configured stations, or a new `WeatherUndergroundStation` for an ID a browser looked up. Cycling through IDs could use up the shared WU quota, so the site must stay on a private network unless a limit is added.
- **Looked-up stations stay in that browser.** They're saved in `localStorage`, with no accounts or server storage. The list holds 20. A full list refuses new stations until one is removed, rather than dropping one, because the dropped station could be the browser's default.
- **Forecast and alert locations stay in Core.** `StationLocator` supplies them through `IWeatherStation.GetCoordinatesAsync`, using `DefaultLocation` for the home station. `/api/daily-forecast` and `/api/alerts` return the station's configured name, or the ID for a looked-up station, never coordinates or a neighbourhood. So a looked-up station's home page shows its neighbourhood while its forecast shows its ID.
- **Alerts never show last good data.** An old alert could be wrong, so a failed check says alerts are unavailable, which must never look like "no alerts". NWS and USNO only add detail, so their failures hide a section rather than the page.
- **The home station stays on Ambient Weather.** Weather Underground is only for the other stations in `Stations`. It updates less often, reports less and has a shared quota. In the app, someone without Ambient keys gets `OpenMeteoStation` under the `home` ID through `HomeStationSource`.
- **`LocalApi` must match the controllers.** Any change to an endpoint's defaults, validation or status codes goes in both, and `LocalApiTests` compares them.
- **The app's keys stay on the phone.** They're entered in setup and kept in `SecureStorage`. They only cross the bridge going in: the client is told whether a key is saved, never what it is. App backups stay off.
- **The app never shows other sites.** `appBridge.ts` sends external links to the system browser, because a page loaded in the WebView has no way back and can reach the bridge. `OpenLink` accepts `https` only.
- **App-only client code stays out of the site.** Test `import.meta.env.MODE === 'app'` directly where it decides what loads, because the `isApp` export doesn't let the build drop it.
- **Colours follow the device by default.** Auto sets no attribute on `<html>`, so `index.css` uses `prefers-color-scheme`. Light and Dark set `data-theme`, and the choice is saved in that browser's `localStorage`. Any new colour needs defining for both themes, and dark values live in two blocks of `index.css` that must stay identical.
- **The station page layout stays in that browser.** Card and chart order and which are collapsed are saved in `localStorage` (`stationCards` and `stationCharts`, through `useSortableLayout`), keyed by title and shared by every station. Renaming a card in `stationCards.ts` or a chart in `StationCharts.tsx` drops it from saved layouts.
- **The temperature unit stays in that browser.** It's saved in `localStorage` and set only in Settings, not on individual pages.
- **The Help and Privacy pages describe what the site does.** Adding a data source, anything stored in the browser, or a host the browser calls directly means updating them, and changing `PrivacyPage` or `TermsPage` means updating its effective date.
- **A browser's default station stays in that browser.** It's saved in `localStorage` and sets which station every page starts on, with no accounts or server storage. The home station is the fallback, including when a saved station is no longer configured.
- **Keys go in .NET user-secrets**, never in `appsettings.json`, the repo or chat.
- **All caching is in memory.** Don't add a database or disk storage for forecasts.

## Adding a forecast source

1. Add a class in `Weather.Core/Sources` implementing `IForecastSource`, with its column from `SourceColumns` in `Weather.Core/Models`. Every source is named there once, with a header of 5 characters or fewer, so both tables show the same name. Never change an existing id.
2. Register it in `ServiceCollectionExtensions.cs`. Columns sort by days of data, and that position only breaks ties.
3. Add tests to `SourceTests.cs` using a stubbed response.
4. If it needs a key, return `SourceResult.NeedsKey()` when none is set, and add its options to `WeatherOptions`.
5. Add it to the data sources on `HelpPage.tsx` and `PrivacyPage.tsx`, and give it a hover description in `weather.client/src/sourceDescriptions.ts`.

The table needs no client changes; columns come from the API.

## Source quirks

- **ECMWF:** Open-Meteo returns null for the last two days of the 16-day range.
- **Open-Meteo models:** listed once in `OpenMeteoModels` in `ServiceCollectionExtensions.cs` and used by both tables. Days of data differ: HRRR and HRDPS about 2 (HRDPS covers only the northern US), Météo-France about 4, CMA about 5, ICON and UKMO about 7, GEM and JMA about 10, NBM about 11, ECMWF, AIFS and GFS 15 or 16. NBM and HRRR are US only. GraphCast, BOM and KMA return no snowfall, so they aren't used.
- **WeatherNext:** the ensemble mean, from Open-Meteo's separate ensemble endpoint, about 14 days. Averaging 64 members mutes long-range highs. Open-Meteo's FAQ says ensemble APIs need a paid plan, though the free host answers today, so it may stop.
- **NewsCenter Maine:** an HTML scrape of `/10-day`, Maine ZIPs only. Dates have no year, and the page drops today during the afternoon, so blank NCM cells for today are normal.
- **Weather Underground:** the key only allows the `5day` endpoint, which returns 6 days. The 7, 10 and 15-day endpoints return 401. Personal, non-commercial use only.
- **Morning low and afternoon high:** the table shows each date's morning low (the night that ends that morning) and afternoon high, because that's what people mean by a day's low and high. Midnight-to-midnight values mislead when a front passes: on 2026-11-07 Open-Meteo's calendar-day high was 59 at 2am while the afternoon reached about 50. `DayParts.Merge` joins day and night forecasts by these rules.
- **Open-Meteo lows and highs:** worked out from `hourly=temperature_2m` with `past_days=1`: the low is the coldest hour from 7pm the evening before to 9am, the high the warmest from 9am to 7pm. A window needs every hour but one (for a spring clock change), so a model's last day often has no high.
- **NWS:** about 7 days. Evening forecasts have no high for today. A night period's low goes on the morning it ends.
- **NewsCenter Maine lows:** each row shows the day's high and the low of the night after it, as TV forecasts do, so the parser puts the low on the next date. On 2026-11-05 the Nov 6 row's 48 couldn't be that morning: hourly forecasts stayed at 56 or above all day Nov 6.
- **Weather Underground lows and highs:** from `daypart[0].temperature`, which alternates day and night for each date. The day part is the high, and the night part is the next date's morning low. Today's day part is null once it's over. `calendarDayTemperatureMax` and `Min` are midnight to midnight and aren't used.
- **Consensus:** the Temperature Forecast's Consensus column is the mean and range of the columns shown, worked out in the client (`consensus.ts`) because hiding a column changes it. It's never coloured, because highlighting is decided in Core.
- **Normal lows:** ACIS station search needs both `maxt` and `mint` normals, so lows are never left unhighlighted by a highs-only station. If either average is still missing, `AverageMessage` says which.
- **Station ZIPs:** the Temperature Forecast ZIP box uses, in order, the ZIP a looked-up station was found by (saved in `localStorage`), a configured station's optional `Zip`, the ZIP in an `om-` ID, then the home ZIP. A station looked up by ID has no ZIP.
- **Climate station:** `ClimateStations` picks one ACIS station per location for both the comparison table's averages and the almanac, so they always agree. It's the nearest with `maxt` and `mint` normals whose measured highs and lows began at least 30 years ago and ran within the last 7 days, searching 0.3° to 3° out. It's cached for 30 days, and "none nearby" for a day. Closed stations are never used: Brunswick, the only Brunswick station in ACIS, closed in 2010, so Topsham uses Durham (since 1994). There's no active station in Brunswick to use instead.
- **Almanac:** records come from `StnData` with `sdate: "por"`, `smry` and `groupby: ["year", "MM-DD", "MM-DD"]`. ACIS's summaries skip accumulated multi-day totals, so records are true one-day values (Poland's Irene total of 3.39A on 2011-08-29 isn't its record). Daily values are text: `T` is a trace (sent as `AlmanacRow.TraceInches`), while `M`, `S` (included in a later total) and a value with a trailing flag such as `3.39A` (an accumulated total) are all missing. Each ACIS call has its own timeout. Today's and tomorrow's values are the `/daily` forecast, so a failed forecast only blanks them, while an ACIS failure hides the almanac. It still shows while a station is offline. Each day's sun and moon come from the same cached USNO call as `/daily/{date}`, with Open-Meteo's sunrise and sunset used where the forecast has the date so both pages agree; yesterday's sun is USNO's. A failed forecast or USNO call drops them. `/api/almanac` names the climate station because the averages and records must credit it; it's a public climate site, not the weather station's location.
- **Ambient Weather:** needs both an `apiKey` and an `applicationKey`. It allows 1 request a second per key and returns 429 above that, so `AmbientWeatherStation` runs calls one at a time with a gap. History comes in 5-minute steps and can lag by up to 10 minutes. `hourlyrainin` is a rate in in/hr, not an hourly total. Field names and meanings follow Ambient's Device Data Specs wiki: most battery fields are 1=OK and 0=low, but `batt_lightning` and `batleak1`–`4` are 1=low. `lightning_distance` is already in miles. The outdoor `aqi_pm25` fields were removed in 2023, so the only AQI is indoor (`aqi_pm25_in`, or the AQIN's `aqi_pm25_aqin`), and `co2` is a standalone CO2 meter while the AQIN's indoor CO2 is `co2_in_aqin`. The home station has none of these add-ons, so they're checked only against the specs.
- **Station lookup:** `/v3/location/near?postalKey=ZIP:US&product=pws` returns the 10 nearest stations in parallel arrays. Its `updateTimeUtc` doesn't show when a station last reported: stations hours old by that value had readings from minutes ago. `StationLookup` ignores it and checks `/current` nearest first, through `StationService`'s cache, taking the first with a temperature and a reading from the last hour, because some send only a reading or two. A station with an unreadable reading or its own 4xx is skipped, but 401, 403 and 429 stop the scan because every other station would fail too. That's up to 11 calls for an uncached ZIP, and the result is cached for an hour. An unknown ID and a silent station both return an empty body from `/current`, so they can't be told apart.
- **Weather Underground stations:** the PWS key reads any station ID, through `/v2/pws/observations/current` and `/all/1day`. Limits are reported as 1,500 calls a day and 30 a minute, shared with the WU forecast column, which is why results are cached for 5 and 15 minutes and nothing polls in the background. A station silent for an hour returns an empty body. History covers the current local day, not 24 hours. Many stations have no UV or solar readings, and some have no rain gauge.
- **Open-Meteo Daily Forecast:** `precipitation` is liquid equivalent, including melted snow, while `snowfall` is depth, and `precipitation_unit=inch` returns both in inches. `timezone=auto` applies today's UTC offset to the whole range, so `OpenMeteoOutlook` corrects times after a clock change. Daily totals still follow that fixed offset, so they can be an hour out on those days.
- **Open-Meteo daily weather codes:** the daily `weather_code` is the day's worst hour, so one cloudy hour before dawn makes a sunny day Cloudy. `OpenMeteoOutlook` keeps it for fog, rain and snow, and uses the most common daylight hour for dry days, with ties going to the cloudier code.
- **Open-Meteo stations:** IDs are `om-{zip}`, and looking one up uses no Weather Underground calls or key. `current` covers a 15-minute interval, so its `precipitation` is scaled to in/hr. History is hourly, so `HistoryMaxGapMinutes` keeps the charts joined. The day's rain and top gust stop at now, because later hours are forecast.
- **Station trends:** `TrendCalculator` works out the high, low and 3-hour pressure trend from the history `/api/station` already fetched, so they cover the charts' range (24 hours for the home station, the current day for Weather Underground) and the labels must say which. Steady is under 0.02 inHg and rapid is 0.06 or more, compared after rounding to 0.01. The earlier pressure is the point nearest 3 hours back, within 30 minutes, so a Weather Underground station has no trend until 3am. Like the sky, they're left out unless the station is reporting.
- **Station sky:** stations don't report conditions, so `StationSky` asks Open-Meteo for `weather_code` and `is_day` at the station's location, cached for 15 minutes. The report waits for it, so it has a 3-second timeout of its own. It's modelled, so it can disagree with the readings beside it and the page must credit Open-Meteo. A failure or an offline station hides it. Its location comes from `StationLocator`, shared with alerts, so it adds no Weather Underground calls.
- **NWS alerts:** `/alerts/active?point=` with `status=actual&message_type=alert,update`. `limit` returns 400 on that endpoint. Times are in the alert area's local time, so they're shown as issued. Severity can be missing. `expires` is when the message lapses, not when the event ends, so it's never shown as an end time or used to hide an alert.
- **NWS descriptions:** about 7 days, so later days have none. A night period starting after midnight belongs to the previous date. The precipitation shown with a description comes from Open-Meteo's hours for 6am to 6pm or 6pm to 6am, skipping past hours, so it can differ from the day's total.
- **NWS discussion:** the Area Forecast Discussion from `/products/types/AFD/locations/{office}`, then `/products/{id}` for its text. The office code comes from the cached gridpoint forecast URL, so it adds no `/points` call. `NwsDiscussion.Parse` splits sections on `.TITLE...` lines and `&&`, and stops at `$$`, where the forecasters' names follow. Its watches and warnings section is always dropped: alerts never show old data, and that list is as old as the discussion. Like the descriptions, a failure hides it.
- **USNO moon data:** the moon doesn't rise or set every day, so either time can be missing. The `tz` value is for that date, with `dst=false`.
- **Radar:** the browser calls NOAA's `conus_bref_qcd` WMS and OpenStreetMap's tiles directly, so there's no server code. `GetCapabilities` lists about 60 scans over two hours, and the page uses the first scan of each ten-minute slot plus the newest, so frames stay stable as scans arrive. OpenStreetMap's tile policy requires its attribution to stay visible and suits light use only.
- **Map types:** the Maps page (`/radar`) shows one type at a time, set in `mapModes` in `api/radar.ts` and reset to Radar on reload. Precip type is `conus_pcpn_typ` from the same NOAA GeoServer as radar. Its legend image has no labels, only seven equal blocks coded WS, S, C, H, CS, ST and CT: MRMS precipitation flags 1, 3, 6, 7, 10, 91 and 96 (warm stratiform rain, snow, convective rain, rain with hail, cool stratiform rain, tropical stratiform and tropical convective). `precipTypeKey` describes them and the page lays a hover or tap zone over each block. MRMS has no sleet, freezing rain or mixed category. nowCOAST's cloud legend is a grey ramp labelled 0 and 255, so Clouds draws its own warmer-to-colder scale, and the warnings overlay has no usable legend, so its note links to the NWS colour key. Clouds (GOES infrared, 5-minute steps) and lightning (strike density, 15-minute steps) come from nowCOAST; warnings are opengeo's `wwa:hazards`, shown at their newest time under the lightning. Each GeoServer layer has its own `/geoserver/{workspace}/{layer}/ows`, and `readLayerTimes` reads the named layer's Dimension. Temperature is NWS NDFD from `mapservices.weather.noaa.gov` through ArcGIS `export`, one Web Mercator tile per request. It's a forecast, not observed. Only the group layer `show:0` draws: it shows the earliest still-valid 3-hourly image, and asking for any sublayer alone returns a blank image. `time` has no effect, and the legend is 1°F swatches read from `legend?f=json`. A newer temperature image comes as a new layer keyed by `imageVersion`, swapped in once it loads; never `redraw` it, because Leaflet clears every tile first, which blanked the map whenever the tab regained focus.
- **Snow Forecast:** sources implement `ISnowSource` in `Weather.Core/Snow` and return periods (start, end, low and high inches), so `SnowWindow` can total any dates from one cached result, sharing a period that crosses midnight. Totals run midnight to midnight in the town's time zone, and a source whose periods start after the window or end before it is `Partial` (NWS and WU drop hours already past today), shown with ≥ and left out of the client's averages. Averages are worked out in the client because manual rows and the source filter change them. Towns come from `SnowTowns` in config; a browser's added and removed ZIPs are in `localStorage`. `SnowTableService.Parse` validates for both the controller and `LocalApi`.
- **Snow ranges:** `SnowText` reads ranges from forecast text: NWS `detailedForecast` ("New snow accumulation of 1 to 3 inches possible", "little or no" is 0 to 0.5) and WU day-part narratives ("Snow accumulations around one inch"). NWS uses those ranges for their 12-hour periods and gridpoint `snowfallAmount` (mm, ISO 8601 intervals) for the rest. Gray (GYX) fills snow grids only about 3 days out, so a longer range shows NWS as ≥. Open-Meteo answers a burst of calls with 429, so `OpenMeteoSource` and `OpenMeteoSnowSource` ask for all models on one endpoint in a single call per location (`temperature_2m_{model}`, `snowfall_{model}`), through `OpenMeteoRequests`, which runs three calls at a time. WU uses `qpfSnow` when the narrative has no range, and shares the `wu-daily:{zip}` response with the temperature column so both pages cost one call. Open-Meteo `snowfall` with `precipitation_unit=inch` is depth, per preceding hour.
- **WeatherAPI.com:** snow only, from `forecast.json` hourly `snow_cm`. The free plan forecasts 3 days, so `WeatherApi:ForecastDays` is 3. The key goes in the query string as `key=`.
- **TV snow totals:** NewsCenter Maine, WMTW and WGME publish snow totals only as map images. Their pages have no amounts in HTML, WMTW's robots.txt and the TEGNA and Sinclair terms forbid scraping, so they're manual rows typed in the browser and kept in `localStorage` until cleared. Don't add scrapers for them.
- **AccuWeather:** removed on purpose. Its API has no lasting free tier and its website blocks automated requests. Don't scrape it, or Weather Underground's pages.
